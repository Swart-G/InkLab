# Облачное сохранение InkLab через папку Google Drive

Статус: проектная спецификация, интеграция ещё не реализована. Дата сверки официальной документации: 8 сентября 2026.
Связанные документы: [формат и сохранность](DOCUMENT_ARCHITECTURE.md), [задачи и приёмка](IMPLEMENTATION_TASKS.md).

## 1. Пользовательский контракт

InkLab работает полностью локально без входа в Google. После явного подключения сохраняет редактируемые версии в обычной видимой папке Google Drive. Пользователь может открыть папку, скачать `.inklab` и восстановить его вручную. Облако — отдельная подтверждаемая копия, а не условие работы редактора.

Различать три функции: локальный autosave; облачная история/восстановление; двусторонняя синхронизация между устройствами. Первый облачный milestone допускает upload + восстановление, но называется «Облачные копии». Название «Синхронизация» разрешено только после прохождения сценариев двух устройств.

MVP: один Google-аккаунт и одна корневая папка на одну локальную облачную библиотеку, личный My Drive. Shared drives, совместное редактирование с другими людьми и несколько одновременно активных аккаунтов — за рамками. Папка может наследовать доступ из родительской папки: приложение не меняет sharing автоматически, UI объясняет выбранное место хранения. Публичные ссылки не создаются.

## 2. Выбор транспорта и доступ

Выбран Drive REST API v3 с OAuth-полномочиями пользователя. Не использовать старый Android Drive API или локальную «папку Drive» как якобы гарантированную файловую систему. SAF остаётся для ручного импорта/экспорта; наличие URI не обеспечивает change feed, надёжный revision protocol и фоновый доступ API.

Стартовый scope — `drive.file`, ограниченный файлами, созданными/открытыми через приложение. Предпочтительный основной путь — создать новую папку InkLab приложением и сохранять туда созданные им файлы. Хранить ID папки, а не её название: одинаковые имена допустимы. `appDataFolder` не подходит как единственное хранилище, поскольку пользователь просит обычную видимую папку.

Выбор существующей произвольной папки — отдельный обязательный feasibility spike. Нельзя предполагать, что доступ к папке даёт рекурсивный доступ ко всем вручную добавленным в неё файлам при `drive.file`. Проверить поддерживаемый Google Picker/явный grant-flow на Android, создание дочерних файлов, чтение на втором устройстве и после переустановки. Не заменять этот flow обычным SAF picker с последующим выдуманным Drive ID.

Если минимальный scope не покрывает требуемый повторный доступ, сначала предложить явное открытие нужных файлов/папки через поддерживаемый grant-flow. Более широкий scope — отдельное решение с обоснованием, consent и оценкой требований Google; не расширять разрешения молча. До завершения spike UI гарантирует только проверенный сценарий app-created папки. Критерий облачного выпуска обязательно включает второй девайс и чистую установку с тем же production OAuth project.

## 3. Инфраструктура и авторизация

До реализации подготовить Google Cloud project, включённый Drive API, OAuth consent и Android OAuth client с package name и SHA сертификата подписи. Разделить debug/test и production-конфигурации; для APK вне магазина проверить фактический release signing certificate. При наличии web picker зарегистрировать только необходимые web client/origin/redirect согласно выбранному flow. Зафиксировать владельца проекта, используемые client IDs и инструкцию воспроизводимой настройки в integrations/GOOGLE_DRIVE.md на этапе реализации.

В APK не вшивать service-account key или OAuth client secret. Авторизация пользовательских данных через поддерживаемый Android authorization flow; вход в аккаунт и предоставление Drive-доступа — разные состояния. Не хранить самостоятельно долгоживущие refresh tokens без необходимости выбранного официального механизма. Получение/обновление access token изолировать от sync engine; авторизация, требующая UI, возвращает состояние «Нужно войти снова».

Проверить приложение в тестовом consent-режиме и production, отказ пользователя, истечение/отзыв доступа, смену аккаунта, отсутствие Google Play services. При недоступности Google-интеграции всё локальное продолжает работать, доступны ручной `.inklab` и экспорт PDF. Не обещать длительную автономную фоновую авторизацию на основании короткого успешного теста.

Наблюдаемость без собственного сервера: локальный диагностический журнал операций sync и экспорт по действию пользователя. Записывать коды причин, длительности, байты и обезличенные operation IDs; не писать токены, содержимое заметок, URL resumable session, полные account/folder IDs. Автоматической отправки заметок в аналитику нет.

## 4. Подключение и настройки

Путь: Настройки → Облачное сохранение → Google Drive → аккаунт/согласие → создать папку или выбрать проверенный доступный вариант → выбор документов → первоначальная синхронизация.

На экране показать аккаунт, название и ссылку на папку, объём выбранных данных, настройку «Только Wi-Fi», включение аудио и статус. По умолчанию предлагать все локальные документы; фактическую загрузку начинать после завершения явного подключения. Изменение выбора документа прекращает новые uploads, но не удаляет уже существующие версии. «Удалить облачные копии» — отдельное действие.

При найденной существующей библиотеке проверить libraryId и версию протокола; показать «Подключить существующую» или «Создать отдельную». Не объединять библиотеки по совпадению названий. Первая синхронизация сначала инвентаризирует удалённые данные, затем сопоставляет ID и revisions, и только после этого планирует uploads/downloads.

## 5. Структура папки и идентичность

| Элемент | Назначение | Правила |
|---|---|---|
| Корневая папка InkLab | Видимое место хранения | rootFolderId + account binding + libraryId |
| library descriptor | Версия протокола и libraryId | Создаётся при инициализации; не общий изменяемый индекс документов |
| documents / documentId | Контейнер версий одного документа | Имя может содержать удобный title, но идентичность по ID |
| revisionId.inklab | Полный самодостаточный snapshot | Новый Drive file для каждой версии; завершённые файлы неизменяемы |
| metadata events | Папки, перемещения, переименования папок и tombstones | Неизменяемые события с ID и причинными родителями |
| exports (опционально) | PDF для чтения | Производные файлы, не источник sync |

Это логическая раскладка, которую реализация отображает в Drive folders. Подпапки библиотеки внутри InkLab хранятся метаданными, а не обязаны повторять физические Drive folders. Так переименование учебного предмета не требует перемещать все старые версии. При необходимости человекочитаемое зеркало/экспорт можно добавить позже.

Идентификаторы: libraryId — библиотека; documentId — документ; revisionId — неизменяемая версия; parentRevisionIds — причинные предки; operationId — повторяемая транспортная операция; deviceId — случайный ID установки без аппаратного fingerprint; remoteFileId — ID конкретного файла Drive. updatedAt используется для отображения, не для определения победителя.

Не полагаться на уникальность имён: Drive допускает дубликаты. Два одинаковых revisionId с одинаковым hash дедуплицируются логически; различный hash при том же revisionId — повреждение/коллизия, файл изолируется, автоматическое применение запрещено. Индекс/head-файл допускается только как восстанавливаемый кэш, не единственный источник истины.

## 6. Почему неизменяемые версии

Обычная перезапись одного `.inklab` двумя устройствами может молча уничтожить предыдущую редакцию. Сравнение modifiedTime до upload не закрывает гонку между проверкой и записью. Drive не считать многодокументной транзакционной базой или распределённым lock-сервисом.

Каждое устройство публикует новый самодостаточный snapshot с parentRevisionIds. Головы вычисляются как версии без известных потомков. Одна голова — обычное продолжение; две независимые головы — конфликт. Даже если второе устройство публикует устаревшую ветку после завершения проверки первого, обе остаются в папке и конфликт обнаруживается при следующем обходе. Это проектный протокол InkLab поверх Drive, а не встроенная гарантия Drive.

Цена MVP — повторная передача больших PDF/аудио в полном пакете. Сначала обеспечить корректность. После измерений допустим второй формат с неизменяемыми content-addressed assets и manifest, публикуемым последним; для него отдельно доказать восстановление, garbage collection и совместимость. Самостоятельный экспорт `.inklab` при этом остаётся полным.

## 7. Публикация локальной версии

1. Координатор получает подтверждённую локальную последовательность документа. Незавершённые изменения в памяти не помечаются отправленными.
2. После паузы 15 с собрать неизменяемый snapshot. При непрерывном письме ориентир — не реже одной попытки snapshot за 2 минуты в foreground, с учётом размера и ресурсов. Кнопка «Сохранить в Drive сейчас» снимает debounce.
3. Зафиксировать revisionId, parents, operationId, локальную последовательность и путь staging в durable outbox до сетевого запроса. По возможности заранее зарезервировать remote file ID для идемпотентного создания; поддержку подтвердить на spike.
4. Проверить архив, hashes и свободное место. Открытый аудиосегмент исключить с явной отметкой полноты; завершённые сегменты включить согласно настройке.
5. Отправить через resumable upload. URL сессии и смещение сохранять приватно, чтобы продолжить после process death; это чувствительные данные, не диагностический текст.
6. При сомнительном результате запроса сначала выяснить, завершена ли сессия/создан ли файл, используя сохранённый ID и operationId. Повтор не должен порождать новый revisionId. Если физический дубль всё же возник, дедуплицировать по revisionId + hash.
7. После финального ответа проверить metadata, размер и контрольную сумму там, где API её предоставляет; записать application hash. При первом восстановлении обязательно пересчитать SHA-256 распакованных данных. Upload не считается успешным по одному факту создания metadata.
8. Атомарно сохранить локальное acknowledgement этой revision. Если за время upload появились новые операции, UI показывает оставшиеся изменения; подтверждение старой версии не означает отправку текущей.
9. Получить изменения Drive и проверить появление параллельной головы. Не отменять местные правки ради удалённой версии.

Зависшие staging/upload-файлы не считаются опубликованными без валидного полного контейнера. Sweep таких объектов консервативен, не трогает незнакомые пользовательские файлы. Сжатие/упаковку ограничивать по CPU/IO; не перезапускать большой upload на каждый новый штрих. В outbox можно объединять только ещё не начатые промежуточные снимки, сохраняя последнюю локальную версию и её причинную базу.

## 8. Фоновые задачи и сеть

WorkManager — планировщик устойчивой очереди, а outbox — источник истины. Unique work на account/library и последовательная обработка одного documentId предотвращают локальные дубли; это не блокировка другого устройства. Сохранённые операции переживают перезапуск и reboot. При принудительной остановке/ограничениях Android немедленное выполнение не гарантируется: возобновить при разрешённом запуске и показать фактическое время последней копии.

Триггеры: локальный commit с debounce, открытие/закрытие документа, запуск приложения, доступная сеть через constraints, ручной retry. Периодическая работа — страховка, а не таймер realtime-sync. Без собственного публичного backend не строить обязательные push webhooks. Foreground polling только при открытом облачном документе, ориентир 30–60 с с адаптацией; при фоне полагаться на системный scheduler.

Retry: ограниченный exponential backoff с jitter, учитывать Retry-After. 401 — попытка обновления токена, затем нужна авторизация; 403 классифицировать по причине (права, quota, rate limit), 429/5xx/timeout — повтор; malformed archive/schema — без бесконечного повтора. Нет сети — ожидание constraints. Не держать бесконечный wake lock, не обходить ограничения фоновой работы. Для больших ручных передач отдельно выбрать поддерживаемый Android механизм длительной работы по target SDK на момент реализации.

Начальные лимиты: один upload одновременно, предзагрузка одного remote document, Wi-Fi по настройке. При metered-сети и полном пакете >20 МБ — понятное ручное разрешение на текущую передачу; не запрашивать его повторно для того же operationId. Возможность не синхронизировать аудио отображается в статусе полноты копии, а не скрывается.

## 9. Получение изменений и применение

Начальная инвентаризация: получить start page token до listing, перечислить доступные файлы библиотеки со всей пагинацией, затем обработать изменения от сохранённого token, закрывая окно гонки. Feed охватывает доступные аккаунту/приложению файлы, не только одну папку; фильтровать по известным IDs и принадлежности library. Не принимать совпадение имени за принадлежность.

Каждую порцию feed применить к локальному каталогу и только затем сохранить следующий cursor. При недоступном/отклонённом cursor или сомнительной полноте выполнить повторный listing без удаления локальных данных. Feed отражает текущее состояние файлов и не заменяет историю редакций, которую хранит InkLab.

Remote snapshot сначала скачивается в staging, проверяются схема, manifest, размеры, hashes и все ссылки. Если локальная версия не менялась и remote является потомком её базы, допустим fast-forward. Если редактор активен, применение отложить до безопасной точки без активного пера/IME/выделения; дать индикатор «Есть обновление». Проверить локальную последовательность повторно непосредственно перед commit. Новые местные правки превращают auto-apply в конфликт.

При наличии незагруженных assets документ не считается готовым offline. MVP скачивает полный пакет перед редактированием восстановленного документа; список/preview может появиться раньше. Не заменять рабочую тетрадь частично скачанным содержимым. Локальные viewport и удобные настройки пера сохраняются отдельно от содержимого.

## 10. Конфликты

| Ситуация | Решение MVP |
|---|---|
| Только локальные правки | Новая revision от известной базы |
| Только удалённые, локальная база чистая | Проверенный fast-forward |
| Оба устройства изменили один документ от общей базы | Сохранить обе головы, предложить разрешение |
| Правки разных страниц | В MVP также конфликт документа; автоматический page merge позже |
| Удаление против редактирования | Сохранить редактированную ветку и tombstone, запросить выбор |
| Две одинаковые версии | Дедупликация по revisionId/hash |
| Нет общей базы | Не угадывать: две самостоятельные версии, восстановление копией |
| Неизвестная новая схема | Не применять/не перезаписывать; сохранить пакет и предложить обновление |

Диалог конфликта показывает устройство (пользовательская метка), время как справку, число страниц, preview и изменения при доступности summary. Действия: оставить эту, выбрать другую, сохранить обе отдельными документами. Ни одно действие не удаляет оригинальные ветки немедленно.

Выбор одной создаёт новую resolution revision с обеими известными головами в parents и выбранным содержимым. «Сохранить обе» оставляет исходный documentId у выбранной основной и создаёт новый documentId для второй с полным remap внутренних ссылок; затем фиксирует resolution основной ветки. Повторное применение того же resolution operation идемпотентно. Если во время выбора появилась третья голова, она остаётся нерешённым конфликтом; не помечать всю библиотеку синхронизированной.

Не использовать last-write-wins по часам, не считать номер ревизии одного устройства глобальным. Совместное онлайн-редактирование не обещается; сохранение параллельных версий — обязательная защита даже для личного аккаунта.

## 11. Папки, переименования и удаления

Папка библиотеки имеет folderId, parentId, название, eventId и parents метаданных. Переименование документа относится к его содержимому revision; перемещение документа относится к метаданным библиотеки. Разделение не должно позволять одному событию переписать все папки целым folders.json на Drive.

MVP обрабатывает конфликт двух изменений одного metadata-объекта вручную, не пытается незаметно объединить порядок. Независимые объекты применяются отдельно. Если два одновременных перемещения создают цикл, отклонить результирующий цикл и показать спорные папки в «Требует разбора» под корнем. Недостающий parentId также не делает документ невидимым.

Удаление в InkLab создаёт tombstone с ID, областью, причинной базой и ссылкой на последнюю версию. Удаление папки MVP помещает в корзину только папку, а живые документы/подпапки перемещает в её родителя; каскадное удаление — отдельное явное действие с перечислением. Tombstones хранятся до явного сброса облачной библиотеки; их малый размер предпочтительнее «воскрешения» старым offline-устройством.

Файл исчез из Drive, доступ отозван или root folder в корзине: это не доказательство удаления документа пользователем в InkLab. Приостановить sync, оставить локальную копию, объяснить недоступность папки/версии. Внешнее удаление не распространяется автоматически как wipe локальной библиотеки. Внешнее переименование root не ломает связь по ID. Перемещение неизвестного файла вручную в папку не означает разрешение импортировать его.

## 12. История и очистка

MVP не удаляет опубликованные версии автоматически. UI показывает занятый объём и предоставляет отдельную очистку истории; рекомендуемая будущая политика — последние 20 версий и по одной дневной за 30 дней. Она не становится активной без реализации безопасного GC и понятного выбора пользователя.

При ручной очистке всегда сохранить все текущие головы, нерешённые ветки, явно закреплённые версии и версии, необходимые незавершённым операциям. Причинные метаданные revision/parents сохранять даже после удаления payload, чтобы определить старую ветку вернувшегося offline-устройства. Самодостаточные snapshots позволяют восстановление без полной цепочки payload.

Sync не равен независимому backup: потеря аккаунта или ручное удаление всех облачных файлов может уничтожить историю Drive. Поэтому оставить отдельный экспорт библиотеки и ручной `.inklab`. Не обещать бессрочное восстановление через внутренние Drive revisions/trash. Полное удаление облачной библиотеки — отдельная явная команда, никогда не следствие «Отключить».

## 13. Смена аккаунта, папки и восстановление

Отключение: остановить workers, отменить сессии по возможности, сохранить локальные документы и облачные файлы. Удалить локальные credential bindings и приватные session URLs. Outbox пометить привязанным к старому account/library и не отправлять в новый аккаунт. При повторном подключении — сверка, а не слепой replay.

Смена папки: предложить подключить существующую библиотеку или создать новую с копированием выбранных локальных документов. Это не команда переместить/удалить старую папку. При смене аккаунта явно показывать назначение будущих uploads; разрешённые ранее документы не переносить скрытно в чужой аккаунт.

Чистая установка: авторизация → выбор/обнаружение доступной библиотеки → listing → выбор документов → download → проверка → установка с сохранением ID. Дублированный вручную `.inklab` в локальную библиотеку импортируется только явным режимом копии. Потерянный descriptor восстанавливать по согласованным libraryId пакетов через recovery flow; неизвестные смешанные библиотеки автоматически не объединять.

## 14. Статусы и критерии сервиса

| Состояние | Текст/поведение |
|---|---|
| Local dirty | «Сохранение на устройстве…» |
| Local durable, cloud off | «На устройстве сохранено» |
| Очередь | «На устройстве сохранено · Ожидает Drive» |
| Upload | Фактический прогресс байтов, если размер известен |
| Подтверждённая актуальная revision | «В Drive сохранено», время |
| Активное/исключённое аудио | «Конспект в Drive · Аудио ещё не сохранено/не включено» |
| Offline / Wi-Fi constraint | «Ожидает сеть/Wi-Fi», без модального окна |
| Auth / root unavailable | Понятная причина и действие в настройках |
| Conflict | «Две версии — требуется выбор», обе сохранены |
| Local storage failure | Постоянное заметное сообщение, статус успеха запрещён |

Foreground-цели при стабильной сети ≥10 Мбит/с upload и пакете ≤5 МБ: отправка после debounce p95 ≤60 с; обнаружение версии на открытом втором устройстве ≤90 с. Для больших пакетов показывать объём и измеренную скорость, не обещать тот же срок. Background не имеет жёсткого SLA из-за Android scheduler.

Критерии надёжности: ноль потерь подтверждённых данных; повтор upload/apply не создаёт логических дублей; после 100 прерываний в разных фазах восстановление приходит к целостному состоянию; две offline-ветки сохраняются независимо от порядка reconnection; без сети все основные функции редактора работают. Конкретная матрица — в [задачах](IMPLEMENTATION_TASKS.md).

## 15. Открытые решения и обязательные доказательства

До включения флага sync закрыть: повторный доступ `drive.file` на втором устройстве/переустановке; поддерживаемый Android flow выбора существующей папки; идемпотентное создание с зарезервированным ID; metadata/checksum и завершение resumable upload; реальная стоимость полного snapshot с P2/A1; механизм продолжительной фоновой передачи на целевых Android. Для каждого сохранить короткий ADR: варианты, проверка, принятое решение, ограничение. Не заменять непроверенное допущение рекламной формулировкой в UI.

## 16. Официальные основания

- [Drive API scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth): область `drive.file` относится к конкретным доступным приложению файлам; минимальный доступ предпочтителен.
- [Android authorization](https://developer.android.com/identity/authorization): авторизация доступа к пользовательским данным Google.
- [Folders](https://developers.google.com/workspace/drive/api/guides/folder): работа с папками и родительскими ID.
- [Resumable uploads](https://developers.google.com/workspace/drive/api/guides/manage-uploads): транспорт больших файлов с возможностью продолжения.
- [Changes feed](https://developers.google.com/workspace/drive/api/guides/manage-changes): получение token и постраничная обработка изменений.
- [WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent) и [unique work](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/manage-work): устойчивое планирование и исключение локального дублирования задач.

Структура revisions, конфликтная модель, лимиты и SLA выше — собственные архитектурные решения InkLab; ссылки подтверждают платформенные возможности, а не реализацию этого протокола.
